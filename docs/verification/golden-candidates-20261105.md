# 분석 사례집 W01~W60 업데이트·골든셋 후보함 검증 — v0.2.5 (2026-11-05 ~ 11-10)

기준: PR #12(`codex/worked-casebook-20261104`, bbf8a6c, 그 아래 v0.2.4 브랜치 367ca51 포함) 위에 브랜치 `claude/golden-candidates-20261104`로 골든셋 후보함을 더하고, 기존 0.2.4 설치에 적용하는 Windows x64 오프라인 업데이트 매체를 만들었다. 합성 자료·격리 QA 설치만 썼다. 운영 서버·운영 자료·실제 은행 자료(`var/objects`, `INV-20261008-001`)·기존 매체와 태그는 바꾸지 않았다.

이 매체는 **후보**다. 대상 Windows 10 Enterprise LTSC 2019에서 실행하지 못한 항목은 PENDING_ENV로 적었고, "운영 적용 검증 완료"로 부르지 않는다.

## 1. 골든셋 후보함

| 동작 | 구현 | 확인 방법 |
|---|---|---|
| 담기 | 사례집 W 상세와 조사 ④ 확인 및 판단의 "골든 후보로 담기" 한 번. 메모는 선택 | 서버·화면 시험, 실제 브라우저 |
| 저장하는 것 | 원본 식별자와 버전만. 사례는 사례 JSON의 SHA-256, 조사는 증거 파일들의 SHA-256. 로그를 복사하지 않음 | 서버 시험 |
| 중복 | 같은 출처·같은 버전은 한 건(동시에 두 번 눌러도 한 건) | 서버 시험, 실제 브라우저 |
| 권한 | 조사 후보는 그 조사의 열람 권한을 따름. 권한이 없으면 목록·수정·빼기·저장·내보내기 모두 404이고 제목·ID가 보이지 않음 | 서버 시험, 실제 브라우저(권한 없는 합성 계정) |
| 빼기 | 후보 행만 지움. 원본 조사·로그·저장한 골든 버전은 남음 | 서버 시험 |
| 골든 저장 | 내부 골든 버전을 재사용. 사례는 `casebook:Wxx` 합성 기록으로 저장. 조사에 이미 내부 골든 기록이 있으면 새 초안으로 덮어쓰지 않고 현재 버전에 연결 | 서버 시험 |
| 내보내기 | 선택한 저장본만 `agent-input.jsonl`/`evaluator-answer.jsonl`로. 두 파일은 같은 example_id. 입력에는 중립 제목만 있고 사례 번호·사례 제목·후속·결론 문장이 없음. 후보함의 분할이 그대로 나감 | 서버 시험(사례 60개 전부), 실제 브라우저 |
| 데이터베이스 | 마이그레이션 0026: 표 `kn_golden_candidate` 1개 추가만, 있으면 건너뜀 | 서버 시험(SQLite), 설치 리허설(PostgreSQL) |

## 2. 자동 시험

- 서버 전체 r13(a32996d): 3,064건 중 3,023 통과·41 건너뜀(환경 조건)·실패 0·오류 0. 독립 검토 수정 뒤 최종 커밋의 전체 결과는 저장소 STATE와 릴리스 설명에 적는다.
- 화면 65파일·429건 통과, TypeScript 오류 0(독립 검토 수정 뒤).
- 독립 코드 검토(읽기 전용, 별도 검토자): 치명 0건. 중요 3건과 작은 지적 5건을 고치고 시험을 붙였다.
  - 조사 후보를 저장할 때 손으로 다듬은 기존 골든 버전을 새 초안이 조용히 대체하던 것 → 기존 기록이 있으면 현재 버전에 연결.
  - 후보함에 보이는 분할과 내보낸 분할이 다르던 것 → 후보함의 분할을 그대로 내보냄.
  - 에이전트 입력에 사례 번호(예: W26)가 남아 정답 파일을 가리킬 수 있던 것, 2단계 설명이 나중 검증을 암시할 수 있던 것 → 번호를 지우고 2단계 설명을 입력에서 뺌. 이전에 저장한 버전도 내보낼 때 지운다. 사례 60개 전부에 대해 시험.
  - 작은 지적: 사례 첫 저장 동시 요청 시 500 → 400 안내, 없는 골든 기록 내보내기 방어, 안 쓰는 import, 느린 첫 조회가 "후보함에 있음" 표시를 지우던 경쟁, 이미 열린 사례집에서 `?worked=` 바로 열기가 무시되던 것.
  - 고치지 않고 남긴 것은 §6.

## 3. 실제 브라우저 (격리 QA 서버, 합성 자료, 사용자가 직접 로그인한 합성 계정 manager)

- 사례집: 사례 60개·단계 300개·화면 그림 120장·사례 ZIP 60개(각각 fw.csv/ndr.csv/followup.json).
- W26 재현(시험 조사, 107,032행 적재):
  - 로그 직접 검색 → 출발지 10.80.26.15 + 로그 종류 connection = 121건.
  - 목적지 포트 445를 더하면 2건(14:06:03 98,304B / 14:06:21 154,624B, fw.csv 60,192·60,193행). 두 행 모두 근거 시간 14:04:00~14:08:22 안.
  - followup.json의 W26-E1(파일 감사 14:06:07)·E2(EDR locksvc.exe 218개)·E3(백업)와 호스트·IP·계정·시각이 일치.
- 후보함:
  - W26을 두 번 담아도 1건. W26 시험 조사도 ④에서 담음.
  - 권한 없는 합성 계정(스크립트 로그인)에는 W26만 보이고 조사 제목·ID가 없음. 조사·원문은 403.
  - W26만 골든 v1로 저장. 내보내기: 파일마다 1줄, 같은 ID, 입력에 후속·결론 없음, 평가 파일에 compromise_confirmed·W26-E1~E3, 선택하지 않은 조사는 두 파일 모두에 없음.
  - 새로 고침 뒤에도 후보 유지.
- 참고: 개발 QA 서버는 SQLite라 10만 행 업로드 2개를 동시에 처리하다 "database is locked"가 나 W26 작업의 분석 단계가 실패로 끝났다(적재·색인은 완료). 제품 설치본은 PostgreSQL이다.

## 4. 설치 (매체에 든 이 문서에는 최종 매체의 결과가 없고, 저장소·릴리스 설명에 기록한다)

- 앞선 후보 매체(a32996d 빌드, ZIP 1,571,706,069바이트, SHA-256 71e42fb6…, manifest 92d4af5c…, schema 0026)로 개발 PC 합성 설치 리허설 a17을 실행했다: 54단계 = 계획한 차단 실패 1 + PASS 53, 88분.
  - 게시된 v0.2.4 매체(schema 0025)로 설치 → UPDATE-SAW 창 단추 동작으로 0.2.5 업데이트.
  - 신규 설치·재개·재시작, 별도 백업/복구, 주입 실패 뒤 자동 복구, 업데이트 성공 뒤 "이전 상태 복구"로 0.2.4·자료 복귀, 두 번째 업데이트, 같은 매체 재적용.
  - 후보 추가·저장 → 재적용 뒤 유지·내보내기.
  - 사례집 확인 3회: 60/300/120/60, ZIP 내부 FW 3,953,128행·NDR 2,474,232행.
  - 각 비교에 전역 조사·증거·탐지·작업·이벤트 건수를 넣어, 사례집을 열어도 운영 자료가 늘지 않음을 확인.
- 이 문서가 든 최종 매체는 독립 검토 수정과 문서를 포함해 다시 빌드했고, 같은 리허설을 새 설치(a18)에서 다시 실행한다. 그 결과와 ZIP 크기·SHA-256은 저장소 STATE와 릴리스 설명에 있다.

## 6. 경계(미검증·제한)

- PENDING_ENV: 대상 Windows 10 Enterprise LTSC 2019(17763)에서의 설치·업데이트, 관리자 서비스 방식·재부팅, native OpenSearch/PostgreSQL 운영 구성과 대용량 성능. 시험한 Windows는 개발 PC의 Windows 11 Pro 26200(NoAdmin 사용자 프로세스 방식)뿐이다.
- 운영 서버는 업데이트하지 않았다.
- 후보함의 남은 제한
  - 내보내기는 파일 두 개를 차례로 받는다. 두 번째가 실패하면 첫 파일만 남으므로 다시 내보낸다.
  - 조사가 삭제되면 그 조사 후보는 목록에 나타나지 않는다(행은 남음).
  - 조사를 담으려면 조사 쓰기 권한이 필요하고, 권한이 없으면 기존 조사 API와 같이 403이다. 메모·분할 변경·빼기는 지식 쓰기와 조사 열람 권한으로 가능하다.
  - 후보 목록은 한 번에 최대 2,000건을 읽고 검색어마다 권한을 다시 확인한다. 후보가 아주 많을 때의 응답 시간은 재지 않았다.
  - 지식 쓰기 권한이 없는 계정에도 "골든 후보로 담기"가 보이며, 누르면 권한 안내가 나온다.
