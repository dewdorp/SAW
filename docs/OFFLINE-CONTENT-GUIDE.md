# 외부에서 준비한 룰·파서를 폐쇄망에 반입하기

이 기능은 외부 준비 PC에서 만든 **Sigma 룰·선언형 파서 JSON**을 서버 화면으로 반입합니다. 반입만으로 현재 탐지는 바뀌지 않습니다. 합성 예제를 시험하고, 반입한 사람과 다른 선임·매니저가 **승인·적용**해야 공용 콘텐츠가 됩니다.

이 기능을 포함한 앱과 스키마 0013이 먼저 필요합니다. 기존 2026-10-12 설치 ZIP에는 포함되어 있지 않습니다. Windows LTSC 2019 실장비 인수와 앱 설치 매체 갱신은 별도입니다.

## 먼저 따라 하는 실습: r1 → r2 → 되돌리기

처음에는 운영 로그 대신 아래 합성 파일로 연습하세요. r1은 특정 경로 하나를 찾고, r2는 두 번째 경로를 추가하면서 파서가 상태 코드도 읽도록 바꿉니다. 되돌리면 r1의 내용으로 돌아갑니다.

| 준비 파일 | 용도 |
|---|---|
| [synthetic-rules-parsers.json](../examples/content-packages/synthetic-rules-parsers.json) | 최초 반입 r1. Sigma 1개와 파서 1개, 합성 시험 4개 |
| [synthetic-rules-parsers-r2.json](../examples/content-packages/synthetic-rules-parsers-r2.json) | 수정본 r2. 같은 두 항목의 원본 버전을 2로 올림, 합성 시험 6개 |
| [synthetic-demo.log](../examples/content-packages/synthetic-demo.log) | r1·r2·되돌리기 결과를 비교하는 합성 로그 3건 |
| [synthetic-demo-r2.log](../examples/content-packages/synthetic-demo-r2.log) | r2 파서의 선택적 상태 코드 필드를 확인하는 합성 로그 2건 |
| [SHA256SUMS.txt](../examples/content-packages/SHA256SUMS.txt) | 두 JSON 파일의 파일 전체 SHA-256 |

실습 계정은 작성·반입 담당자 A, 승인·적용 담당자 B, 복구 검토자 C로 구분합니다. B와 C에는 `detection.approve`와 `parser.approve` 권한이 모두 필요합니다. 예제는 룰과 파서가 한 묶음이기 때문입니다. 계정과 권한은 관리자가 기존 절차로 준비하며, 이 문서에는 로그인 비밀값을 넣지 않습니다.

예제의 `package_id`는 `saw-synthetic-demo`, 룰 `source_id`는 `demo-sensitive-path`, 파서 `source_id`는 `demo-appliance`입니다. 이 예제를 이미 적용한 서버에서 처음부터 반복하려고 같은 ID·버전을 덮어쓰지 마세요. 별도 시험 환경을 쓰거나, 검토한 별도 ID로 실습 파일을 다시 만들어야 합니다.

### 1. 외부 준비 PC에서 파일을 만들고 반입 매체에 담기

처음 실습은 위의 r1·r2 JSON과 합성 로그 파일을 그대로 준비합니다. 직접 만드는 경우에는 준비 PC에 같은 버전의 SAW와 Python 환경이 있어야 합니다. 준비 PC의 SAW 화면 또는 아래 명령 도구로 작성·검증할 수 있습니다. 운영 서버에서 인터넷 다운로드나 소스 빌드는 하지 않습니다.

파일을 수정했다면 `build`로 새 지문을 계산하고 `test`로 양성·정상 예제가 모두 통과하는지 확인합니다. 조직의 반입 절차에 따라 JSON, 시험 기록, 파일 지문을 함께 가져갑니다. 계정·운영 원문·모델 파일은 이 콘텐츠 묶음에 넣지 않습니다.

### 2. A가 r1을 반입하고 B가 적용하기

1. A로 **오프라인 룰·파서** 메뉴를 엽니다. 화면은 **1. 파일 만들기 또는 불러오기 → 2. 반입·적용 이력 → 3. 시험·승인·적용** 순서입니다.
2. **JSON 파일 불러오기**에서 `synthetic-rules-parsers.json`을 선택합니다.
3. **파일 검증·변경 미리보기**를 누릅니다. `demo-sensitive-path`와 `demo-appliance`가 모두 **추가·원본 v1**인지 확인합니다.
4. **반입 초안 저장**을 누릅니다. 이때는 현재 룰과 파서가 바뀌지 않습니다.
5. 이력에서 **saw-synthetic-demo r1**을 선택하고 **양성·정상 합성 예제 시험**을 누릅니다. 4개 예제의 통과 결과를 확인합니다.
6. B로 로그인하여 같은 이력을 엽니다. 조건·예제·지문을 검토하고 사유를 입력한 뒤 **승인·적용**을 누릅니다. A는 자신의 반입본을 적용할 수 없습니다.
7. 적용자·시각·사유와 **적용됨** 상태를 확인합니다.

이제 별도의 합성 시험 조사를 만들고 작업대의 **증거 추가**로 `synthetic-demo.log`를 올립니다. 처리 기록에서 파서 `u:demo-appliance`, 버전 1, 기록 3건을 확인합니다. 승인된 Sigma 결과의 **일치한 기록**은 1건이어야 합니다. 다른 탐지기의 표본 부족 안내가 함께 나올 수 있으므로 화면의 전체 카드 수와 Sigma 일치 건수를 혼동하지 마세요.

### 3. r2로 룰과 파서 바꾸기

1. A가 `synthetic-rules-parsers-r2.json`을 불러옵니다. r1을 적용한 다음에 r2를 반입해야 합니다.
2. **파일 검증·변경 미리보기**에서 두 항목이 모두 **변경·원본 v2**인지, 변경 전후 조건이 예상과 같은지 확인합니다.
3. 초안 저장과 합성 예제 시험을 실행합니다. r2는 6개 예제가 통과해야 합니다.
4. B가 독립 검토한 뒤 사유를 적고 **승인·적용**합니다.
5. 새 합성 시험 조사에서 같은 `synthetic-demo.log`를 처리합니다. 파서 버전 2, 기록 3건, Sigma **일치한 기록 2건**을 비교합니다.
6. `synthetic-demo-r2.log`도 별도 합성 시험으로 처리하면 파서 버전 2로 2건을 읽으며 Sigma 일치는 1건입니다. 이 파일에는 r2가 지원하는 상태 코드 필드가 있습니다.

룰 변경은 이후 실행한 분석에 반영됩니다. 파서 변경으로 기존 색인 필드까지 바꾸려면 기존 증거를 명시적으로 재처리해야 합니다. **조사 재분석만으로 이미 파싱한 필드가 바뀌지는 않습니다.** 실습은 각 단계의 합성 조사에서 새로 처리해 비교하면 결과가 섞이지 않습니다.

### 4. C가 r2를 되돌리기

1. C로 로그인한 뒤 이력의 **saw-synthetic-demo r2**를 선택합니다.
2. **되돌리기 영향 확인**을 누릅니다. 두 항목이 **직전 승인본 복원**, **적용 후 상태 일치**인지 확인합니다.
3. 차단 이유가 없으면 사유를 적고 **확인한 이전 승인본으로 되돌리기**를 누릅니다. B는 자신이 적용한 묶음을 되돌릴 수 없으며, A도 자신이 작성한 이전 Sigma 룰의 복구를 승인할 수 없습니다.
4. **되돌림** 상태와 복구 담당자·시각·사유를 확인합니다.
5. 새 합성 시험 조사에서 `synthetic-demo.log`를 처리합니다. 파서 버전은 1, 기록은 3건, Sigma 일치는 다시 **1건**이어야 합니다.

Sigma 버전 숫자가 1로 낮아지는 것은 아닙니다. **r1의 룰 내용을 담은 보상 버전 v3**를 추가하므로 이전 이력을 보존합니다. 파서는 승인된 v1을 다시 활성화하고 v2는 이력에 남깁니다. 되돌린 r2를 다시 적용하려면 r3와 더 큰 `source_version`으로 새 묶음을 준비해야 합니다.

### 이 실습에서 실제 확인한 범위

2026-10-15 개발 환경의 별도 서버에 실제 HTTP로 반입·합성 시험·다른 사람의 승인·파일 업로드·파싱·분석·되돌리기·내보내기를 실행했습니다. 저장소는 격리한 SQLite와 로컬 객체 저장소이며 합성 파일만 사용했습니다.

| 실행 단계 | 실제 파서 버전 | 읽은 기록 | 해당 Sigma 일치 기록 | 실제 Sigma 버전 |
|---|---:|---:|---:|---:|
| r1 적용 후 기본 로그 | 1 | 3 | 1 | 1 |
| r2 적용 후 같은 기본 로그 | 2 | 3 | 2 | 2 |
| r2 적용 후 상태 코드 로그 | 2 | 2 | 1 | 2 |
| 제3 검토자가 r2를 되돌린 후 기본 로그 | 1 | 3 | 1 | 3 |

이는 실제 API·파서·룰 엔진 검증 결과입니다. **이번 새 화면의 브라우저 클릭 검증과 스크린샷 촬영은 브라우저 도구 장애로 완료하지 못했습니다.** 위 버튼명과 단계는 구현된 화면을 기준으로 작성했으며, 캡처한 화면처럼 제시한 이미지는 없습니다. LTSC 2019 실장비 설치·공동 접속·운영 오탐률 인수 결과도 아닙니다.

## 직접 수정하는 예: 룰 경로 하나와 파서 필드 하나 추가

r1의 Sigma는 `/saw-demo/restricted` 하나를 선택합니다. r2의 `entries` 중 `kind: sigma` 항목의 `content.logic`에는 아래 YAML 내용이 들어갑니다.

```yaml
title: Synthetic restricted paths v2
logsource: {category: webserver}
detection:
  selected:
    cs-uri-stem:
      - /saw-demo/restricted
      - /saw-demo/admin-export
  condition: selected
level: medium
```

JSON 파일에서는 이 YAML 전체가 `logic` 문자열이며 줄바꿈은 `\n`으로 저장됩니다. 완성된 r2 파일을 복사해 해당 항목만 수정하면 JSON 따옴표·줄바꿈 오류를 줄일 수 있습니다. 운영 규칙에서는 `admin` 같은 넓은 단어 하나로 탐지하지 말고 실제로 확인한 경로·필드 조건과 정상 제외 예제를 함께 정합니다.

파서 r2의 `content.spec`은 기존 형식에 선택적 `status` 필드를 붙입니다. 아래는 **JSON 안에 넣는 형식**이므로 정규식 역슬래시를 두 번 씁니다.

```json
{
  "format": "regex",
  "pattern": "^demo src=(?P<ip>\\S+) path=(?P<path>\\S+)(?: status=(?P<status>\\d{3}))?$",
  "mapping": {"ip": "src_ip", "path": "uri", "status": "status_code"},
  "auto_map": false,
  "data_source": "web",
  "detect": {"line_regex": "^demo src="}
}
```

`mapping`은 추출한 이름을 SAW 필드에 연결합니다. `detect.line_regex`는 이 파서가 후보가 되는 로그 형태이고, `pattern`이 실제 한 줄을 해석합니다. 예제처럼 선택적 그룹을 쓰면 기존 상태 코드 없는 형식도 유지할 수 있습니다.

수정할 때는 다음 항목을 함께 확인합니다.

| 항목 | 이번 예제의 변경 |
|---|---|
| 묶음 `package_id` | 같은 묶음의 수정본이므로 유지 |
| 묶음 `revision` | 1 → 2 |
| 각 항목의 `source_id` | 룰·파서 계열 식별자 유지 |
| 각 항목의 `source_version` | 변경한 항목을 1 → 2, 되돌린 뒤에도 최고값보다 증가 |
| Sigma 예제 | 새 경로가 일치하는 양성 예제 추가, `/health` 정상 제외 유지 |
| 파서 예제 | 상태 코드 있는 양성 예제와 기대 `status_code` 추가, 관계없는 로그 제외 유지 |
| `payload_sha256` | 직접 계산·복사하지 않고 **내용 검증·파일 만들기** 또는 CLI `build`로 재생성 |

## 파일 SHA-256과 payload 지문은 다릅니다

**파일 SHA-256**은 반입한 JSON 파일의 모든 바이트를 확인합니다. 공백이나 줄바꿈만 바뀌어도 값이 달라집니다. 예제 폴더에서 아래 명령을 실행해 [SHA256SUMS.txt](../examples/content-packages/SHA256SUMS.txt)의 같은 파일명과 비교합니다. 현재 목록은 두 JSON 파일만 포함하며 합성 로그 파일의 지문 목록은 아닙니다.

```powershell
Get-FileHash -LiteralPath .\synthetic-rules-parsers.json -Algorithm SHA256
Get-FileHash -LiteralPath .\synthetic-rules-parsers-r2.json -Algorithm SHA256
```

**`payload_sha256`**은 문서에서 그 필드 자신을 제외하고, 키 정렬·UTF-8·공백 제거 규칙으로 정규화한 JSON 내용의 지문입니다. 서버는 이 지문을 다시 계산하여 검증합니다. JSON의 들여쓰기만 바꿨다면 payload 지문은 유지될 수 있지만 파일 지문은 달라집니다. 두 종류의 값이 서로 같아야 하는 것은 아닙니다. **파일 검증·변경 미리보기** 화면에 표시하는 것은 payload 지문입니다.

두 지문 모두 발행자의 서명은 아닙니다. 승인된 전달 경로의 지문과 비교하고 내용·예제·출처를 검토해야 합니다. 내용과 지문이 함께 바뀐 파일을 SHA-256만으로 신뢰해서는 안 됩니다.

## 적용이 막힐 때 확인할 것

| 표시·상황 | 확인과 처리 |
|---|---|
| 지문 불일치 | 준비 PC에서 파일 전체 SHA와 전달받은 목록을 비교합니다. 의도적으로 수정한 파일이면 버전을 올리고 `build`·시험 후 다시 반입합니다. 운영 서버에서 지문만 덮어쓰지 않습니다. |
| 같은 ID·revision에 다른 파일 | 이미 저장한 revision은 불변입니다. 새 revision과 증가한 항목 버전을 사용합니다. |
| source_version이 낮음 | 되돌리기 전의 최고 적용 버전도 포함해 더 큰 숫자를 씁니다. 예제 r2를 되돌렸다면 다음은 최소 v3입니다. |
| 현재 룰·파서가 변경됨 / 409 충돌 | 초안 저장 뒤 다른 적용·수동 수정이 있었습니다. 현재 변경을 먼저 검토한 뒤 새 revision으로 다시 미리보기·시험합니다. |
| 합성 예제 실패·시간 초과 | 실패한 양성·정상 예제와 기대 필드를 준비 PC에서 수정합니다. 실패를 무시하거나 시간 제한을 올려 통과시키지 않습니다. |
| 승인·적용 버튼 비활성 / 403 | 시험 통과, 사유, 현재 권한, 반입자와 검토자 분리를 확인합니다. |
| 되돌리기 버튼 비활성 / 403 | 화면의 차단 이유를 확인합니다. 적용자와 이전 Sigma 작성자를 제외한 C 검토자가 필요할 수 있습니다. |
| 되돌리기 중 이후 변경 감지 | 자동 복구를 중단합니다. 이력을 검토해 복원할 내용을 새 수정본으로 준비합니다. |
| 적용했는데 이전 조사 결과가 같음 | 기존 결과는 자동 갱신되지 않습니다. 룰은 명시적 재분석, 파서 필드 변경은 증거 재처리가 필요합니다. |
| 파일 크기·항목 수 초과 / 413 | 지원 한도 안으로 묶음을 나눕니다. 서로 다른 묶음 간에는 하나의 원자적 적용이 보장되지 않으므로 의존 순서를 검토합니다. |

## 화면에서 파일 만들기

1. **오프라인 룰·파서 → 합성 예제 불러오기**를 누릅니다.
2. JSON의 이름·조건·필드 매핑을 수정합니다. 처음 만드는 묶음은 고유한 `package_id`를, 이후 수정본은 더 큰 `revision`을 씁니다.
3. 항목의 `source_id`는 같은 룰·파서 계열에서 유지합니다. `source_version`은 과거에 적용한 최고 버전보다 크게 올립니다. 이 ID는 임의의 기존 로컬 룰과 자동 연결되지 않습니다. 같은 ID의 기존 사용자 파서가 있으면 충돌로 거부됩니다.
4. 모든 항목에 양성·정상 제외 합성 예제를 넣습니다. **내용 검증·파일 만들기**를 누르면 지문을 계산한 JSON 파일을 내려받습니다.
5. 파일을 준비 PC에서 검토하고 조직의 매체 반입 절차로 폐쇄망에 가져갑니다. 실제 조사·은행 원문, 계정, 비밀값을 예제에 넣지 않습니다.

직접 작성한 시작 파일은 [합성 JSON](../examples/content-packages/synthetic-rules-parsers.json)을 참고하세요. 다운로드·외부 접속·임의 코드 실행이 발생하는 파일 형식은 지원하지 않습니다.

## 폐쇄망에서 반입하고 적용하기

1. **JSON 파일 불러오기**를 누릅니다.
2. **파일 검증·변경 미리보기**로 SHA-256, 실행 계약, 항목별 변경 전후를 확인합니다. SHA-256은 파일 내용의 무결성 확인이며 발행자 서명이나 신원 인증이 아닙니다. 지문을 함께 바꾼 다른 작성자의 파일도 유효한 JSON일 수 있으므로 출처는 별도로 확인합니다.
3. **반입 초안 저장**을 누릅니다. 이 단계에는 현재 활성 룰·파서 변화가 없습니다.
4. 반입 이력에서 묶음을 선택하고 **양성·정상 합성 예제 시험**을 실행합니다. 실패·시간 초과가 하나라도 있으면 적용할 수 없습니다.
5. 반입한 사람과 다른 선임·매니저가 같은 묶음을 엽니다. 지문·내용·예제 결과를 검토하고 사유를 입력한 다음 **승인·적용**을 누릅니다. 권한이 변경되었거나 현재 룰·파서가 반입 시점 이후 바뀌면 거부합니다.
6. 적용 결과의 사용자·시각·사유를 확인합니다. 항목 하나가 실패하면 묶음 전체를 취소합니다. 다른 검토자가 같은 기준 상태의 변경을 먼저 적용했다면 뒤 요청은 충돌로 거부됩니다.

시험 종류는 `package_fixture`입니다. 합성 예제 통과는 **실제 과거 조사 재생 시험이나 운영 오탐률 검증을 의미하지 않습니다**. 실제 조사 재생은 기존 탐지 룰 화면에서 별도로 수행합니다. 자동 분석 결과에도 승인 시험 종류를 표시합니다.

적용 후 새 파일 처리나 명시적으로 실행한 조사 재분석에 반영됩니다. 기존 결과를 자동 변경하거나 증거를 재처리하지 않으며 외부 SIEM·센서에 배포하지 않습니다.

## 되돌리기와 이력

적용된 묶음에서 **되돌리기 영향 확인**을 누릅니다. 적용 이후 수동 편집이나 다른 묶음 적용 등 변경이 있으면 되돌리기를 차단합니다.

적용했던 사람과 다른 권한 보유자가 사유를 입력하고 **확인한 이전 승인본으로 되돌리기**를 누릅니다. 이전 Sigma 룰을 복구할 때는 **직전 버전 작성자와 최초 룰 작성자도 복구를 승인할 수 없습니다**. 따라서 작성자 A와 적용자 B만 있으면 되돌릴 수 없는 경우가 있으며, 두 사람과 다른 권한 보유 검토자 C가 필요합니다. 화면에서 차단 이유를 먼저 확인하세요. 처음 추가한 콘텐츠를 끄는 경우에는 이전 룰 복구 승인 조건이 없으며, 파서는 기존 독립 승인 기록을 보존한 채 이전 승인본을 복원합니다. 직전 승인본이 있는 경우만 그 내용으로 복원합니다. Sigma는 예전 내용을 새로운 보상 버전으로 추가하며 이전 버전을 삭제하지 않습니다. 파서는 한 ID에 공용 활성 버전이 하나만 남도록 복원합니다. 처음 추가한 콘텐츠는 삭제 대신 사용 중단합니다.

반입·시험·적용·되돌리기·내보내기를 감사 기록에 남깁니다. 같은 파일의 중복 반입은 기존 기록을 반환하며, 동일 적용 요청을 반복해도 버전을 추가하지 않습니다. 이미 되돌린 묶음은 재적용하지 않으며 새로운 revision과 source_version으로 준비합니다. source_version의 과거 최고값은 되돌리기로 낮아지지 않습니다.

## 지원 형식과 한도

| 항목 | 지원 범위 |
|---|---|
| 파일 | 단일 UTF-8 JSON, 1MiB 이하, 1~20항목 |
| 실행 계약 | `schema: saw.content-package/1`, `requires.content_engine: saw-content-v1` |
| 내용 | 기존 로컬 평가기가 지원하는 Sigma와 CSV/regex/KV/JSON 선언형 ParserSpec |
| Sigma | 로컬 logsource·필드·modifier·시간창/횟수 조건. 별도 `exceptions` 배열은 v1 미지원이므로 Sigma 조건 안에 정상 제외 조건을 작성 |
| 합성 예제 | 항목당 2~8개, 양성 및 정상 제외 필수. Sigma 예제당 1~20이벤트, 파서 예제당 20줄·8192자 이하 |
| 파서 기대값 | 양성 예제에 정규화된 CES 기대 필드. 정상 제외 예제는 자동 감지와 해석이 모두 맞지 않아야 함 |
| 시험 | 전체 시간 예산 5초, 기존 regex 평가 시간 제한 적용 |
| 버전 | 묶음 ID+revision은 불변. 원본 ID별 버전은 과거 적용 최고값보다 증가 |
| 금지 | ZIP, 경로 기반 설치, 스크립트·Python 코드·실행파일, YARA/외부 엔진 룰, 내장 엔진 YAML 교체, 모델 파일 |

알 수 없는 JSON 필드·중복 키·비유한 숫자·지원하지 않는 실행 계약은 거부합니다. 큰 임계값을 가진 Sigma가 20이벤트 이하의 양성 예제로 증명되지 않는 경우에도 적용하지 않습니다. 지원 범위를 벗어나는 내용은 검증 가능한 형태로 다시 작성하거나 별도 앱 업데이트 절차를 사용해야 합니다.

## 준비 PC의 명령 도구

이 앱 소스와 기존 Python 환경이 있는 준비 PC에서 다음처럼 실행할 수 있습니다. 인터넷 연결이나 새 패키지 설치는 하지 않습니다.

```powershell
python -m saw.devtools.content_package example sample.json
python -m saw.devtools.content_package build edited.json content-r2.json
python -m saw.devtools.content_package verify content-r2.json
python -m saw.devtools.content_package test content-r2.json
```

`build`는 문서 계약과 조건을 검증하고 지문을 계산합니다. `test`는 합성 예제를 실제 실행하며 실패하면 종료 코드 2를 반환합니다. 출력 파일이 이미 있으면 덮어쓰지 않습니다. 명령 도구는 서버 반입·승인·적용을 수행하지 않습니다.

## 콘텐츠와 앱 설치 매체의 구분

콘텐츠 JSON은 DB에 저장하는 데이터입니다. 기존 백업의 PostgreSQL dump에 반입 이력·콘텐츠·검증 근거가 함께 포함됩니다. 서버 재시작 후에도 유지됩니다.

Python 코드·UI·DB 마이그레이션·내장 탐지 엔진·런타임 업데이트는 전체 앱 설치 매체의 영역입니다. 현재 `install.ps1`은 신규 설치 전용이며 기존 설치 경로에서 다시 실행하는 업그레이드 도구가 아닙니다. 프로그램 업데이트는 별도 검토된 백업·호환성·전환·복구 절차로 진행해야 합니다.
